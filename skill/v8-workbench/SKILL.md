# V8 客开工作台

## 这个 skill 解决什么

V8 客开有三个反复出现的问题：

1. **平台 API 记不准**。V8 的 SPI/UDC/前端 API 在不同小版本之间有差异，凭记忆写出来大概率是错的，编译能过但运行时找不到实现、或者行为不符预期。
2. **规范是散的**。语雀里 31 篇开发规范（编码、数据库、接口、前端、安全、单元测试…）没人会在写代码前逐篇读完，结果是提交后被打回。
3. **踩过的坑重复踩**。上个项目解决的问题，下个人不知道，重新踩一遍。

工作台把这三件事收口成三个工具。**本 skill 定义的是"什么时候用、按什么顺序用、查到后怎么落地"**，工具本身由 MCP server 或 CLI 提供。

## 工具在前，判断在后

这个 skill 不是知识本身，**不要试图从本文件里找 V8 的技术答案**。本文件只教你流程。真实内容在工作台里。

先确认工作台可用：

```bash
wb health          # CLI 形态
```

如果不可用，告诉用户需要先配置 `V8WB_URL` / `V8WB_KEY`，然后用你自己的通用知识继续，但**明确标注哪些结论没有文档依据**。

## 核心工作流

### 第一步：先定任务类型（必做）

```bash
wb rules spi          # 或 udc / bpm / frontend / integration / data / docs
wb rules "给客户做组织同步"   # 自然语言也可以
```

返回的是该类任务的**必读规范清单 + 提交前自查项 + 常见坑**。

为什么必须先做：这一步会把"该读哪几篇规范"直接列出来，避免你在 231 篇文档里瞎搜，也避免漏掉安全规约、单元测试这类容易忘的项。

MCP 形态等价于 `v8_rules(task)`。

### 第二步：按需展开规范原文

`wb rules` 只给清单和文档 id，不给全文（规范正文加起来几万字，全塞进上下文是浪费）。

**只展开和当前任务真正相关的那几篇**：

```bash
wb read yuque:217357024          # 工程结构
wb read --title "接口规范"
```

判断标准：写后端代码 → 工程结构、接口规范、命名风格；写前端 → 前端目录结构、@seeyon/global、模块联邦。不确定就展开 2-3 篇，不要全展开。

### 第三步：查具体实现

```bash
wb search "组织同步 中间表"
wb search "SPI扩展 登录" -d 扩展能力
```

**query 怎么写** —— 这是决定检索质量的关键：

| 好的写法 | 差的写法 | 原因 |
|---|---|---|
| `组织同步 中间表` | `怎么把用户同步到V8` | 口语词会稀释关键词权重 |
| `SPI扩展 登录` | `登录那块我想改一下` | 要带平台术语 |
| `@seeyon/global 请求封装` | `前端怎么发请求` | 具体 API 名最准 |

第一次没查到，**换更短的术语重试**，不要直接放弃改用记忆。仍然不行就看知识域：

```bash
wb domains
wb search "同步" -d 集成平台
```

### 第四步：读全文，再动手

搜到结果后**必须 read 最相关的 1-2 篇**。搜索结果里的标题和命中词只能说明"可能相关"，不能提供接口签名、配置项、参数含义。直接照着标题写代码是本流程最常见的失败方式。

```bash
wb read yuque:224228683
```

正文超过 6 万字会分段，用返回的 `next_offset` 继续。

### 第五步：自查，再交付

`wb rules` 给出的自查清单逐条过一遍。清单项是**真实项目里出过问题的地方**，不是形式主义。

典型自查项：
- 扩展实现类是否放在客开工程包路径下（没放进平台包）
- 外部依赖是否都有超时和兜底
- 返回值空值语义是否明确
- 是否覆盖了异常路径

### 第六步：沉淀（可选但强烈建议）

任务完成后，如果踩到了**文档里没写、靠试错才搞明白**的坑，沉淀回去：

```bash
wb push ./notes/udc-user-null.md --project 某客户 --tags "UDC,前端"
```

MCP 形态是 `v8_contribute(title, content, project, tags)`。

沉淀的判断标准：**半年后别人搜到这条，能不能直接解决问题**。能就写，不能就不写。

不要沉淀：客户敏感信息、平台文档原文、一次性调试过程。

## 各任务类型的关键提醒

这些是从 checklist 里抽出来的最高频踩坑点，展开在代码里之前先看一眼。

### SPI 扩展（`rules spi`）
- 扩展点接口全名和签名必须与该 V8 版本一致，不同版本会变
- 实现类不要放进 `com.seeyon` 平台包路径
- 扩展点里禁止长耗时同步调用，会拖垮平台线程池
- **永远走扩展点，不要改平台核心代码** —— 升级后全部丢失

### UDC（`rules udc`）
- 3.15 之前的扩展代码构建方式与之后不同，勿混用
- 自定义页面不要直接读平台内部 store
- udcSdk 调用统一封装，不散落在业务代码里

### BPM（`rules bpm`）
- 先分清扩展的是流程按钮、流程触发还是微流程绑定，三者机制不同
- 流程事件里做外部 HTTP 调用会导致流程卡死
- 不要假设节点编码固定，客户会改流程

### 前端（`rules frontend`）
- 平台 API 一律通过 `@seeyon/global`，不直接 import 平台内部模块
- 组件遵循模块联邦暴露约定，避免打进主包
- 依赖版本对齐平台基线，不引入冲突大版本

### 集成平台（`rules integration`）
- 先明确数据流向：V8→三方 / 三方→V8 / 双向
- 确认标识映射的唯一键（账号、组织编码、事项 id）
- 回调必须幂等，支持平台重推
- 组织同步要处理删除，否则离职人员残留
- 待办状态要闭环，否则永远停在待办列表

### 数据库（`rules data`）
- 客开表统一前缀，避免与平台表冲突
- 不直接查询平台内部表，跨版本字段会变
- DDL 与 DML 分离，脚本可重复执行

## 输出格式

处理 V8 客开任务时，回答里要能看出依据：

```markdown
## 需求识别
- 类型：<SPI / UDC / BPM / 集成平台 / 前端 / 移动 / 数据>
- 关键前提：<版本、数据流向、扩展点边界>

## 规范依据
- <文档标题> — <文档路径>
（没有文档依据的判断要明确标注）

## 实施方案
1. <改哪个文件/哪个扩展点>
2. <配置项>

## 自查
- [x] <已确认的清单项>

## 待确认
- <缺的客户参数、没查到的文档>
```

**"待确认"这一节不能省**。V8 客开的绝大多数返工来自"想当然" —— 客户的实际版本、实际流程配置、实际组织编码，都要标出来等确认。

## 版本敏感性

知识库文档多数标注了适用版本（如 `3.18`）。检索结果里 `version_hint` 字段就是它。

**版本不一致时不要直接套用**。做法是：在回答里指出"该文档适用于 3.18，当前项目是 X"，然后建议核对。不要静默采用。

## 不要做的事

- 不要凭记忆写 V8 平台 API —— 先查
- 不要把搜索结果标题当成实现依据 —— 打开读
- 不要一次展开十几篇规范 —— 按任务挑 2-3 篇
- 不要把客户敏感数据写进 `v8_contribute`
- 不要在没查文档时假装查过
